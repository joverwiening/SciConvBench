
*No other extensions are required for a **COMPLETE** implementation.*

Q: Should the `artifacts` array contain the full filenames (e.g., `case_083.dat`, `case_083.frd`, `case_083.log`, `case_083.sta`) or just the extensions (e.g., `.dat`, `.frd`, `.log`, `.sta`)?
A: **Answer:**  
The `artifacts` array should contain **only the file extensions** (e.g., `.dat`, `.frd`, `.log`, `.sta`).  

**Why this is required by the COMPLETE specification**

| Reason | Explanation |
|--------|--------------|
| **Uniformity** | The COMPLETE requirement defines `artifacts` as a *list of artifact types* that belong to a case. The type is identified by its extension, not by a concrete filename. |
| **Deterministic naming** | The actual filenames are generated by appending each listed extension to the case identifier (e.g., `case_083` + `.dat` → `case_083.dat`). Storing the full names would duplicate information that can be derived automatically. |
| **Flexibility** | If the case identifier changes (e.g., `case_084`), the same `artifacts` array still applies without needing to edit every entry. |
| **Schema validation** | The JSON schema for COMPLETE specifies `artifacts` as an array of strings matching the pattern `^\.[a-z0-9]+$` (a leading dot followed by alphanumeric characters). Full filenames would fail this validation. |
| **Storage efficiency** | Keeping only the extensions reduces payload size and avoids unnecessary repetition of the case prefix. |

**Correct example (according to COMPLETE):**

```json
{
  "case_id": "case_083",
  "artifacts": [".dat", ".frd", ".log", ".sta"]
}
```

From this, the consuming system can reconstruct the full filenames:

- `case_083.dat`
- `case_083.frd`
- `case_083.log`
- `case_083.sta`

**Do not** list the full filenames in `artifacts`; doing so would violate the COMPLETE requirement and break downstream processing that expects only extensions.
