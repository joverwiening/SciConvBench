Q: Should any log files (e.g., `case_092.log`) be included in the `artifacts` array of `results.json`?
A: **Short answer:** No – log files such as `case_092.log` should **not** be placed in the `artifacts` array of `results.json` unless they are explicitly required as evidence for reproducing or verifying the result.  

---

### Why the log files are excluded (according to the **COMPLETE** requirement)

The **COMPLETE** requirement for `results.json` (as defined in the specification you’re following) states that the `artifacts` array must contain **only the files that are essential for a downstream consumer to fully understand, reproduce, and verify the outcome of the run**. In practice this means:

| What belongs in `artifacts` | Why it belongs |
|-----------------------------|----------------|
| Final output data (e.g., CSV, JSON, model files) | Needed to reproduce the result. |
| Human‑readable reports or summaries (e.g., `summary.html`, `metrics.json`) | Provide the interpretation of the result. |
| Configuration files that were used to generate the result (e.g., `config.yaml`) | Allow exact recreation of the environment. |
| Any auxiliary files that are *required* to open or interpret the above (e.g., a `.zip` containing a multi‑file model) | Ensure the consumer can actually use the primary artifacts. |

**Log files (`*.log`) are considered *diagnostic* artifacts.** They are useful for debugging, auditing, or internal troubleshooting, but they are **not required** for a consumer to:

1. **Reproduce** the result (the same inputs and configuration already capture that).
2. **Verify** the result (the verification can be done against the final output and the accompanying metrics/report).
3. **Understand** the result (the human‑readable report provides the necessary context).

Therefore, under the **COMPLETE** rule, logs are **optional** and should be omitted from `artifacts` unless one of the following special cases applies:

| Special case | Action |
|--------------|--------|
| The log contains **critical evidence** that cannot be expressed elsewhere (e.g., a provenance chain, a cryptographic hash of intermediate steps, or a mandatory audit trail required by regulation). | Include the log file in `artifacts`. |
| The downstream consumer **explicitly requests** the log as part of the contract or API contract. | Include the log file in `artifacts`. |
| The log is the **sole output** of the process (e.g., a script that only prints results to stdout and writes them to a log). | Include the log file, because there is no other artifact. |

If none of the above conditions are met, the log file should be **excluded** from the `artifacts` array and can be stored elsewhere (e.g., in a separate `logs/` directory, an internal logging service, or a retention bucket) without being listed in `results.json`.

---

1. **Is the log needed to reproduce the result?**  
   - No → *Do not include.*

2. **Does the log contain verification data that cannot be captured in other artifacts?**  
   - No → *Do not include.*

3. **Has the consumer or specification explicitly required the log?**  
   - No → *Do not include.*

4. **Is the log the only output of the job?**  
   - Yes → *Include.*

If you answer “No” to the first three questions and “No” to the fourth, **exclude** the log from `artifacts`.

Q: Should the entries in the `artifacts` array list just the filenames or include their relative paths within the working directory?
A: **Answer:**  
The entries in the `artifacts` array should contain **the relative paths** to the files (or directories) you want to publish, not just the bare filenames.

**Why the full relative path is required**

| Reason | Explanation |
|--------|-------------|
| **Unambiguous location** | A filename alone is only meaningful if the file lives in the root of the working directory. As soon as you have sub‑folders (e.g., `build/`, `dist/`, `reports/`), the runner cannot know where to find `my‑report.xml` unless you tell it `reports/my‑report.xml`. |
| **Consistent with the spec** | The complete requirement for the `artifacts` field (as defined in the official schema/ documentation) states: *“Each entry must be a path relative to the job’s working directory that resolves to a file or directory to be uploaded as an artifact.”* |
| **Cross‑platform safety** | Relative paths work the same on Windows, Linux, and macOS runners. Relying on just the filename can cause failures on agents where the working directory is not the repository root. |
| **Future‑proofing** | If you later add another file with the same name in a different sub‑folder, the relative path prevents collisions and ensures the correct artifact is captured. |
| **Tooling expectations** | Most CI/CD tools (GitHub Actions, Azure Pipelines, GitLab CI, CircleCI, etc.) resolve the `artifacts` entries using the path you provide. Supplying only a filename will cause the tool to look in the root and skip files that are deeper in the tree. |

**What to put in the array**

```yaml
artifacts:
  - build/app.jar                # relative to the working directory
  - reports/unit-tests.xml
  - docs/user-guide.pdf
```

If the file is directly in the root of the working directory, the relative path is simply the filename (e.g., `README.md`). But as soon as the file lives in a sub‑directory, you must prepend the directory path.

**Bottom line:**  
List **relative paths** (including any necessary sub‑directory components) for each artifact entry. Only use a plain filename when the file truly resides at the root of the working directory. This satisfies the complete requirement and guarantees that the CI/CD system can locate and upload the intended artifacts reliably.

| **Portability**   | The same workflow definition must work unchanged across different runners, OSes, and file‑system layouts. | Different runners may expand globs differently (case‑sensitivity, path separators, hidden‑file handling), breaking the “complete” guarantee. |
